## 8. MongoDB on Cloudflare (per-request connection)
- **Problem**: Workers cannot reuse a socket opened by an earlier request; a cached mongoose connection makes the next request hang.
- **Fix** (`lib/db.ts`): on Workers only, every request opens its own `MongoClient`; mongoose's default connection `db`/`client` point to it, so models/routes need no changes. `worker.ts` closes it after the response. Local `npm run dev` / `next start` still use the normal pooled connection.
- **Cost**: ~0.35 s extra per API request on Cloudflare (new connection each time).
- **Database**: MongoDB Atlas, cluster in Mumbai, db `valueplus`.

## 12. Performance Notes
- Heavy APIs: `/api/items`, `/api/reports/stock`, `/api/dashboard/stats` take ~4-5 s, **also on plain Node** — not a Cloudflare problem.
- Cause: MongoDB Atlas sends data at only ~100 KB/s (query runs in 0 ms on the server; 446 items = 380 KB = 3.9 s). Looks like Atlas free/shared-tier throttling (10 GB/week transfer limit). Compression did not help.
- Fix options: upgrade the Atlas cluster (Flex/M10), and/or send only needed fields + caching in the heavy APIs.

## 14. Receive Payment credit used on the next bill
- **Receive Payment** (`/sales/payments`, `components/PaymentModal.tsx`, `POST /api/payments`) with no bill number only lowers the customer's `outstandingBalance` (it goes negative = money on account). It does **not** create an Advance Booking (`customer_advances`) record.
- **Bill form** (`components/InvoiceCreationModal.tsx`): available advance = Advance Booking receipts (`/api/crm/advances`, by phone) **+** the customer's credit (`-outstandingBalance` when negative). Banner shows "Payment Already Received" (or both parts). Booking receipts are used first, then the credit; the credit part is sent as `creditAdjusted`.
- **Server** (`app/api/invoices/route.ts`, step 7.9): caps `creditAdjusted` at the customer's real credit and at `advanceAdjusted`, adds it back to `outstandingBalance`, saves it on the invoice (`Invoice.creditAdjusted`). Only the rest of the advance is taken from Advance Booking receipts.
- **Bill delete** gives the credit back (`outstandingBalance -= creditAdjusted`).

## 16. Profit & Loss — purchases before GST, GST box
- **Basis**: sales (Revenue) and purchases are both shown at their ACTUAL amount, before GST. A purchase bill stores `subtotal` (taxable) and `gst` apart (`subtotal + gst = total`; the purchase form treats the rate as ex-GST), so the actual amount is read, not worked out. `/api/reports/profit-loss` uses `subtotal` (fallback `total − gst` when a bill has no subtotal); debit notes subtract; cancelled bills are skipped.
- **Profit does not change**: purchases are not deducted from profit (Profit = Revenue − COGS − Expenses). COGS = line `costPrice × qty` (cost frozen on the bill at sale time, from the item's `purchasePrice`).
- **Summary fields** (`data.summary`): `totalPurchases` (before GST), `salesGst` (Σ bill-line CGST+SGST+IGST), `purchaseGst` (Σ purchase `gst`, debit notes negative), `netGst = salesGst − purchaseGst`. `totalTaxCollected` (existing, bill-level) equals `salesGst` on current data.
- **P&L page** (`accounting/profit-loss`): card "Purchase Entries (before GST)", statement line "Purchases before GST", and a "GST this period (not part of profit)" box: GST on sales / GST on purchases / net (shows "Net GST to pay" if sales GST is more, else "Purchase GST more than sales GST"). Reports page (`/reports`) "Total Purchases (before GST)" card uses `subtotal` too.
- **Checked** (all-time, live): purchases ₹23,49,873 → ₹19,91,418; GST on purchases ₹3,58,455; GST on sales ₹1,90,281; net GST −₹1,68,174 (credit side). Gross ₹80,072 / net ₹79,538 unchanged. 32 comparisons staging vs production vs the database passed.
- **Open points**: (a) 22 products' master `purchasePrice` looks GST-inclusive (compared with their purchase bills) — would inflate COGS once sold; none sold yet. (b) P&L does not treat credit notes (type `credit-note`) as negative revenue; none exist yet. (c) Net profit only deducts the Expenses page entries (₹534 so far).

## 18. Add a new customer from Receive Payment
- **Where**: Receive Payment (Counter) → Record Payment (customer receipts; the Supplier Payout form is unchanged). `components/PaymentModal.tsx` + `components/payments/CustomerPicker.tsx`.
- **How**: the customer box is a type-to-search field (name, mobile or code). A name not on the list offers "Add “name” as a new customer" (typing a 10-digit mobile that is not on the list offers it with that mobile). It opens the same details as the Customer screen: name*, mobile* (10 digits), group, email, address, state, district/city, PIN, GSTIN, credit limit (shop defaults: Uttar Pradesh / Gorakhpur, Retail, ₹1,00,000). The customer is saved first (`POST /api/customers`), then the payment is recorded against them; the form then treats them as an existing customer, so a retry never adds them twice.

## 30. Live updates over WebSocket (no more polling)
- **Why**: about 25 screens asked the server on a timer (every 4 s to 5 min: bell, approval / estimate / leave / discount pop-ups, tasks, attendance, cash cards, audit ...). Every open app made these requests all day, each one a Worker run plus a new MongoDB connection, which drove the Cloudflare CPU use.
- **How it works now**: one WebSocket per open app at `/realtime`. `worker.ts` checks the login (NextAuth `/api/auth/session`, same-origin only) and hands the socket to the `RealtimeHub` Durable Object (`realtime-hub.ts`, binding `REALTIME`, migration `v2`). It uses the **WebSocket Hibernation API**: an idle socket costs no CPU, and `ping` is answered by the runtime without waking it. After **every successful non-GET `/api/*` call** the Worker sends the path (e.g. `/api/estimates`) to the hub. The hub passes it on to the apps. No data goes over the socket; screens fetch again through the normal signed-in API.
- **Extra announcements** (`publishChange` in `lib/realtime.ts`): new notification → `/api/notifications`, sent only to its recipients (`lib/notify.ts`); approval request created → `/api/approvals` (`lib/change-requests.ts`, back-dated bills in `app/api/invoices/route.ts` and `lib/invoice-full-edit.ts`); WhatsApp outbox row → `/api/whatsapp`; cron auto check-out → `/api/staff/attendance`. Marking a notification read (`PATCH /api/notifications`) is announced as `notification-read`, which is what the tasks page watches for "Read by".
- **In the app** (`components/providers/RealtimeProvider.tsx`, mounted in `app/layout.tsx`):
  - A React Query screen says what it watches with `meta: { live: ["/api/..."] }`; any other code uses `useLive(paths, fn)`.
  - A path also matches everything under it.
  - Changes arriving together are grouped (300 ms), so one save means one refetch.
  - After a dropped connection (phone asleep, network lost) every watcher refreshes once, then the app reconnects with backoff (1 s → 30 s). A hidden or offline app waits until it is back. After 6 failed tries it waits for the app to come back to the front.
  - Shared lists: `CASH_LIVE_PATHS`, `ATTENDANCE_LIVE_PATHS`.
- **New screen that should stay current**: add `meta: { live: [...] }` with the API paths whose writes change its data. **Never add `refetchInterval` / `setInterval` fetches again.**
- **Cron**: was every minute; now `*/5 * * * *`. The 10:00 office-start run and the 15-minute late check still land on time, because India time is UTC+5:30 and the cron fires every 5 minutes. A break-over alert can now come up to 5 minutes after the break ends (was 1).
- **Left on timers on purpose**: these never call the server.
  - The break countdown clock (1 s).
  - The day-close / finance-payout reminder toasts.
  - Waiting for another dialog to close.
  - Asking again for location while the check-in dialog is open.
- **Local `next dev`**: there is no hub, so nothing is pushed. Screens still refresh on focus and mount.

## 32. Geofence: time outside the store
- **Limit (tell the owner)**: the app is a TWA (a website). It can read the location only while it is **open on screen**. When the app is closed or the screen is locked, the time is recorded as **"unknown"**, never as "inside". A background geofence needs a native Android app (plan file `PLAN-geofence-and-staff-filters.md`, Phase 2).
- **Phone**: `components/shared/GeofenceWatcher.tsx`, mounted in the dashboard layout.
  - It runs only for `GEOFENCE_ROLES` (salesman, sales, cashier, manager, accounts, hr; not admin / driver / warehouse), and only while checked in and not checked out.
  - It uses `watchPosition`, with no timers.
  - It reports `POST /api/staff/presence` only when crossing the boundary: back inside within 100 m; outside beyond 150 m (one reading beyond 200 m, or two readings a minute apart). Readings with worse than 150 m accuracy are ignored.
  - It also reports once when the app comes back after at least 2 minutes closed (`event: "resume"`, `hiddenMs`; the hidden time is also kept in localStorage for an app that was swiped away).
- **Server**: `lib/presence.ts` (`recordPresence`, `closeAwayAtCheckout`, `awayTooLongAlerts`).
  - It decides from the reported position itself and ignores impossible jumps (over 60 m/s).
  - It keeps `Attendance.awayPeriods` with `kind` = away / break / unknown, plus `totalAwayMinutes` (away only), `unknownMinutes` and `lastPresence`.
  - Leaving during an approved break counts as `break`; time past the break's end is split off as `away`.
  - Someone outside when the app closed counts as away only up to that moment (`endUncertain`).
  - Check-out and the automatic shift-end check-out close an open period.
  - A presence write that changed nothing sends the header `x-realtime-skip: 1`, so `worker.ts` does not announce it. `QueryProvider` does not refetch on these posts.
- **Alert**: the 5-minute cron (`lib/attendance-alerts.ts`) alerts the Manager and Admin after `AWAY_ALERT_MINUTES` (15) outside, repeated every 15 minutes, never during an approved break.
- **Shown**:
  - the dashboard card "Outside the store now" (`components/dashboard/OutsideNowCard.tsx`; Admin / Manager / HR);
  - the Staff Directory column "Away today";
  - the staff member page: month total, and per day every period with times, minutes and distance;
  - the Attendance page: a line under the hours.
  - `GET /api/staff/presence?date=&staff=` is for Admin / Manager / HR.
- **Numbers** are in `lib/store-location.ts` (`GEOFENCE_*`, `AWAY_ALERT_MINUTES`, `GEOFENCE_ROLES`).
